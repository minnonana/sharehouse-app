# 金沢大学の寮（先魁・北溟）対応 計画書

作成: 2026-10-30。`docs/handover-v2.md` §6 の「ほかのハウスで使う」の第1段階。
目標: **友達づてに広げた各ユニットの代表者が、開発者の手を借りずに始めて、困っても自分たちで直せる**こと。
一般のシェアハウス向けの自由な設定と、本物のログインは次の段階に回す。

進み具合（2026-11-13）: 手順1（土台）と手順2（部屋と組み方の表）は実装・本番公開済み（0007〜0009適用済み）。当番タブ・ホーム・代行APIは `src/lib/duty/plan.ts` 経由で `rooms`・`duty_types`・`duty_rotations` から当番を組む（組み方が無いハウスは従来の `rotation.ts` にフォールバック）。アプリ未参加の住人の名前は `rooms.resident_name` に入れて当番表に出す。残り: 定時通知（Edge Function）はまだ固定ローテーションのコピーで動いている／担当をまとめた枠の交換は未対応／参加時に `members.room_id` を入れていない（部屋番号で照合している）。次は手順3（代表者の設定画面）。

計画からの変更: `duty_rotations` は `duty_type_ids` ではなく `slots`（jsonb。`[[担当id,…],…]`、空の配列が休み）を持つ。担当をまとめた枠を、あとでまとめ方の設定が変わっても過去の週の表示が崩れない形で残すため。

## 1. 前提

| | 先魁 | 北溟 |
| --- | --- | --- |
| 1ユニットの最大人数 | 8人 | 5人 |
| ゴミの収集日 | 金沢市（今の日程） | 先魁と同じ |
| 部屋番号 | 代表者が入力する（例: 110 111 112 …） | 同左 |
| 担当のひな形 | 今の7担当（1Fキッチン／1Fトイレ／2Fトイレ／玄関／燃えるゴミ月／燃えるゴミ木／水金） | 5人用（案: キッチン・リビング／シャワー・洗面・トイレ／燃えるゴミ月／燃えるゴミ木／水金）※トイレの数・階を確認中 |

## 2. 決まったこと

1. ハウス作成時に「寮（先魁／北溟）」を選び、ユニットの**全部屋の番号**を入力する（空室も含む）。担当は寮のひな形が自動で入る。
2. 部屋ごとに「入居中／空室」を持つ。**代表者が設定画面で切り替える**（アプリ未参加の住人がいても当番が抜けないよう、自動判定はしない）。
3. 当番は入居中の部屋だけで回す。アプリ未参加の住人の部屋にも割り当て、表には部屋番号だけ表示する。
4. 入居中の数が変わったら、**次の日曜から**組み直す（今週はそのまま）。組み直すときは一周の最初から始め、担当回数をそろえる。
5. 人数が減ったら、まず休みを減らし、足りなければ**決めた順に担当を自動でまとめる**。
6. まとめが進んで1人の負担が大きくなるとき（下の表の「確認」の行）は、**代表者に確認してから**反映する。
7. まとめ方（どの担当をどれにまとめるか、順番）は、代表者が**あとから設定画面で変えられる**。

### 人数ごとの組み方（先魁の例）

| 入居中 | 担当 | 休み | 代表者の確認 |
| --- | --- | --- | --- |
| 8人 | 7担当 | 1人 | 不要 |
| 7人 | 7担当 | なし | 不要 |
| 6人 | 玄関を2Fトイレにまとめて6担当 | なし | 不要 |
| 5人以下 | さらにまとめる（水金→木のゴミ など） | なし | **必要** |

北溟は5人で休みなし、4人からまとめる。3人以下で代表者に確認する（案）。

## 3. データの地図の変更（案）

| テーブル | 変更 | 理由 |
| --- | --- | --- |
| `rooms`（新規） | id, house_id, room_number, is_vacant, sort_order, created_at | 部屋が「空室かどうか」という状態を持つ名詞になったため。部屋番号を1か所にまとめる |
| `houses` | dorm_type（sakigake／hokumei）を追加 | ひな形の選択と、確認が必要な人数の判定に使う |
| `duty_types` | merge_into_id（足りないときにまとめる先）、merge_order（まとめる順）を追加 | まとめ方を代表者があとから変えられるようにする |
| `duty_rotations`（新規） | id, house_id, starts_on（日曜）, room_ids, duty_type_ids, confirmed_by, created_at | 「いつから、どの部屋で、どの担当で回すか」の区切り。過去の週の表示を崩さず、次の日曜から組み直すため |
| `members` | room_id（rooms を参照）を追加。room_number は移行後に使わない | 部屋の二重登録を防ぐ（入居中の住人は1部屋1人まで） |

- 1つのハウスは、たくさんの部屋・担当・組み方の区切りを持つ。
- 1つの部屋には、住んでいる住人が最大1人いる。
- 新しいテーブルには必ず RLS を付ける（自分のハウスだけ読める、変更は代表者だけ）。
- 今の先魁のユニット（111〜118、基準週 2026-09-27）は、今と同じ値で `rooms`・`duty_rotations` に移し、見た目も当番も変えない。

## 4. 作る順番

各ステップの最後に、スマホ幅の画面で操作して確認し、DB変更はマイグレーション（`0007_…`）をユーザーにSQL Editorで実行してもらう。

1. **土台**（完了）: 代表者が住人の復旧コードを出せる（ログインが切れた人を、ユニットの中で直せる）／名前の変更／部屋の二重登録の防止
2. **部屋と組み方の表**（完了。定時通知の切り替えは残り）: `rooms`・`duty_rotations` を作り、今の先魁を移す。当番の計算を「入居中の部屋数に合わせて回す」形にし、担当をコードではなく表から読む。今の表示が変わらないことをテストで確認
3. **代表者の設定画面**: 入居中／空室の切り替え、まとめ方の変更、確認が必要なときの確認画面
4. **ハウス作成画面**: 寮の選択、部屋番号の入力
5. **北溟のひな形**を入れ、5人ユニットで確認
6. 友達のユニットで試してもらう

## 1. このアプリは何か

最大8人の多国籍シェアハウス向けの共用アプリ。掃除当番（週替わり）、洗濯機の使用中表示、掲示板（日英自動翻訳）、買い物リスト、共用費（月500円）をスマホ1つにまとめる。ログインは匿名ログイン＋招待コード（電話番号・LINE・メール不要）。PWA（ホーム画面に追加して使う）。

最初の利用者は金沢大学の学生寮「先魁」と「ほくめい」の住人。実際の当番表（スプレッドシート）と、アプリのローテーションが一致することを確認済み。

## 3. ドラフトから変わったこと

- 当番の表示名: 月・木は「燃えるゴミ(月)」「燃えるゴミ(木)」。水金は、その週に実際に出すゴミの種類（資源・あきびん・燃やさないごみなど）を表示する（`getWedFriDutyLabel`）。
- 当番の見た目: 「完了」と「未完了」を同じ強さで並べず、**済んだ人は薄く、まだの人だけが濃く残る**。自分の行を強い色で塗りつぶすのはやめた（左に細い線だけ）。共用費も同様（払った人は薄く、まだの人は「!」で目立たせる）。
- 買い物リスト: チェックボックスではなく、**「行けるよ」ボタン**で担当になる。担当になるとチェックボックスが出て、完了時に金額を入力する。
- 掲示板: 投稿時にカテゴリ（ルール／来客／修理・工事／その他）を選び、一覧はカテゴリごとに絞り込める。
- 掲示板・買い物の品名は日英に自動翻訳して保存（失敗したときは原文のまま）。
- 画面の下タブ: iPhoneのホーム画面アプリでホームインジケーターに近すぎたため、`viewport-fit=cover` と `env(safe-area-inset-bottom)` で余白を確保。
- 速度改善（2秒→0.5秒前後）: `getCurrentMember()` をリクエスト内で使い回し（React `cache`）、members と houses を1クエリにまとめた。各ページの独立した問い合わせを `Promise.all` で並列化。認証チェックを `getUser()`（毎回ネットワーク）から `getSession()`（Cookieをその場で読む）に変更（middleware とページ側の両方）。実行リージョンを日本に移した。
- 部屋番号のカスタマイズ（ハウスごとに接頭辞を変える、部屋数を変える）は**一度作って取り消した**（マイグレーション0007/0008は削除済みで、本番DBには未適用）。`rotation.ts` の関数は、省略可能な `roomNumbers` 引数を持つ（既定は111〜118）。

## 4. 技術メモ（つまずきやすい点）

1. **`insert().select()` は、挿入した行を読み戻せないと失敗する。** 参加直後は自分の members 行がまだ無く、「自分のハウスだけ見える」というSELECTポリシーで読み戻せない。エラー文は INSERT 違反と同じ `new row violates row-level security policy`。→ ID（`randomUUID()`）をアプリ側で発行し、`.select()` を付けずに insert する（`api/house`、`api/join` はこの形）。
2. RLS は `SECURITY DEFINER` のヘルパー関数（`auth_house_ids()`、`auth_member_id()`、`auth_is_owner()`）を使う。members のポリシーの中で members を直接参照すると無限再帰になる。
3. PostgREST のスキーマキャッシュで、列追加が反映されないことがある。`alter table` のあとは `select <列> from <表> limit 1;` で確認する。`NOTIFY pgrst, 'reload schema'` で足りないこともあり、SQLを再実行して直ったことがある。
4. 認証: middleware が `getSession()` で匿名ログインを維持し、セッションが無いときだけ `signInAnonymously()`。Route Handler の `api/*` は一部まだ `getUser()` を使っている（動作は問題ないが、速度を優先するなら `getSession()` に揃えられる）。
5. **デプロイの手順**（GitHub連携の自動デプロイは使っていない）: `git push` のあと、`npx vercel@61.0.0 --prod --yes --scope 260925-vive-cording`。**バージョンを必ず固定する**（`npx vercel` だけだと最新版61.1.0が応答なしで固まる）。ビルドには数分かかるので、バックグラウンドで実行して出力ファイルを確認する。
6. Gitの作者情報は、グローバルで `zuzu64048@gmail.com` / `minnonana` に設定済み。
7. 秘密情報（Supabaseのキー、VAPID秘密鍵）は `.env.local`（コミットしない）。Vercelの環境変数にも設定済み。
8. テスト: `npx vitest run`（17件。当番ローテーションと共用費の残高計算）。同時操作や参加フローの自動テストは無い。

## 5. 既知の不具合・未解決

- **ログインが突然切れて入れなくなる（再現条件は不明）。** 代表者（オーナー）本人が経験した。匿名ログインはCookieだけが頼りなので、Cookie・サイトデータの消去、ホーム画面アイコンの作り直し、リフレッシュトークンの更新が同時リクエストで競合した場合などが疑われる。引き継ぎコードをSQLで発行して復旧した（下の「復旧手順」）。根本対策は **§6 の「本物のログイン」**。
- `api/join` の「その部屋番号が埋まっていないか」の確認は、**参加前の人にはSELECTポリシーで他人の行が見えないため、常に「空き」と判定される**。同じ部屋に2人入れてしまう。DB側に `unique (house_id, room_number) where left_at is null` を付けるか、`SECURITY DEFINER` 関数で判定する。
- 本番の実ハウスに、試験用のメンバー「DebugTest3」（116号室）と「発表用」（111号室、`hanako` に改名予定）が残っている。ユーザーに設定画面から退去させてもらう。
- ドラフトの未決事項（112・115の名前、会計担当、買い物の上限額、大家への画面など）は、まだ決まっていない。

### 復旧手順（入れなくなった人がいるとき）

SupabaseのSQL Editor（プロジェクト `eqeypmnhyvvamttucnpa`）で、その人の members 行に引き継ぎコードを作る。

```sql
insert into handover_codes (member_id, code, expires_at)
select id, '654321', now() + interval '24 hours'
from members
where name = '名前' and left_at is null;
```

本人は参加画面の「機種変更・アプリ削除後に戻る場合はこちら」にコードを入れる。iPhoneは **Safariとホーム画面のアイコンでログイン情報が別**なので、アイコン側でも同じ手順が必要（コードは `unique` なので別の番号にする）。

## 6. 次にやること（新しい要望）

発表のあと、**別のシェアハウスの住人から「自分たちも使いたい」と申し出があった。** 今のアプリは、`create-house`（代表者がハウスを作る）と招待コードで複数のハウスを持てる作りだが、中身は先魁・ほくめい専用の前提が多い。以下は候補で、**優先順位と範囲はユーザーに確認してから着手すること**（部屋数の可変は以前いったん見送りにした経緯がある）。

### 6-1. ほかのハウスで使うために必要なこと

| 項目 | 今の状態 | 方向性（案） |
| --- | --- | --- |
| 部屋数・部屋番号 | 111〜118の8部屋に固定（`ROOM_NUMBERS`） | ハウスごとに部屋リストを持つ。`rotation.ts` の `roomNumbers` 引数が土台になる |
| 担当の種類・数 | 7担当＋休みの8枠に固定 | ハウスごとに担当を設定。人数と担当数が合わないときの回し方（休みの数）を決める |
| ゴミ収集カレンダー | 金沢市の分別・収集日を `rotation.ts` に直書き | ハウスごとに設定（地域・曜日）。最初は「ゴミ通知なし」を選べるだけでも良い |
| 共用費 | 月500円、共用費の文言が固定 | ハウスごとに金額を設定 |
| 基準週 | `BASE_WEEK_START = "2026-09-27"` で全ハウス共通 | ハウスごとに開始週と、最初の担当の割り当てを持つ |
| 最大人数 | 8人 | ハウスごとの上限 |
| 言語 | 日本語・英語 | 追加の希望があれば言語ファイルを足す（`src/lib/i18n/`） |
| 翻訳 | MyMemory（無料・不安定） | 利用が増えるなら有料APIに切り替え、利用量の上限を確認 |

### 6-2. 土台の安定化

1. **本物のログイン**（優先度が高い）: 匿名ログインはCookieが消えると本人に戻れない。メール（マジックリンク）や、LINE以外の手段など、電話番号がなくても使える方法を検討し、**既存の匿名アカウントを引き継げる**移行方法を決める。ドラフトでは「LINE・大学メール・電話番号は全員が持つとは限らない」としているので、方式はユーザーと相談。
2. 部屋の二重登録を防ぐ（§5）。
3. 管理用の画面または手順: 試験データの削除、メンバー名の変更（今は名前を直す機能が無く、SQLが必要）、ハウスの削除。
4. 費用と上限の確認: Supabase・Vercelの無料枠、プッシュ通知の量、Edge Functionの実行回数。ハウスが増えたときの定時通知の処理時間。
5. 自動テストの追加（参加・退去・同時操作・RLS）。今は当番の計算しかテストが無い。
6. プライバシー: ほかのハウスの住人の名前・投稿は他ハウスから見えないこと（RLSで制御済み）を、ハウスを増やす前にもう一度確認する。公開リポジトリなので、実在の住人名や秘密情報をコミットしない。

### 6-3. 進め方のお願い

- 一度に全部やらず、「ほかのハウスが最低限使える」ところまでを最初の目標にする（例: 部屋リストと担当をハウスごとに設定できる → ゴミ収集を設定または無効にできる）。
- DBの変更は新しいマイグレーション（`0007_...`）を `supabase/migrations/` に足し、**ユーザーにSQL Editorで実行してもらう**。実行後は `select` で反映を確認する。
- 変更ごとに、スマホ幅のブラウザで実際に操作して確認する。速度（画面遷移）を悪化させない（各ページで問い合わせを直列にしない）。
